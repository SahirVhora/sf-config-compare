# Migration investigation pilot

This is the first local, command-line slice of a persistent migration assistant for
SF Config Compare. It consumes this project's existing `quality_analysis.findings`
from `/api/v1/compare`; it does not replace the deterministic rules engine.

## Try the synthetic demo (Python 3.11+, no packages or credentials needed)

Run from the repository root:

```bash
python -m core.investigator ingest examples/investigation-findings.json --scope synthetic:source-to-target
python -m core.investigator run
python -m core.investigator list
python -m core.investigator export db/investigation-review.json
```

The three examples are generated by the actual configuration rules: reduced
maximum field length, a missing target field, and a target-only field. These are
configuration checks, not employee-record or overlapping-employment validators.

Open the exported JSON to see each original finding, proposed correction,
verification checklist, task status, and event history. Offline mode uses the
existing rule's correction text plus a standard verification checklist. It is
explicitly labelled deterministic; it does not perform AI diagnosis.

## Your real workflow

1. Save a comparison API response as a local JSON file.
2. Review/sanitise it before optional AI use. Field/object names and descriptions
   can be confidential even when there are no employee records.
3. Ingest it with a scope such as `client-code:DEV-to-UAT:release-4`.
4. Run the worker and export the review report.
5. Investigate the proposed correction, validate in a test environment and obtain
   sign-off through your existing process. The pilot never applies fixes.

Use separate `--db` paths per client; scope is a deduplication namespace, not an
access-control boundary. Repeat imports of unchanged evidence in the same scope
reuse tasks. Changed evidence produces a new task. Historical tasks are not
automatically closed or marked resolved by a later clean comparison.

## Optional model-assisted investigations

Install `openai` into your project's virtual environment, and configure
`OPENAI_API_KEY` and `OPENAI_MODEL` in the process environment. The CLI does not
load `.env`. Use a model supporting Chat Completions JSON mode and `max_tokens`,
as used by this project's existing AI analyser. `OPENAI_BASE_URL`, when set,
is handled by the SDK; choose an approved compatible endpoint.

```bash
python -m core.investigator --db db/ai-pilot.sqlite3 ingest examples/investigation-findings.json --scope synthetic:source-to-target
python -m core.investigator --db db/ai-pilot.sqlite3 run --ai --limit 3
python -m core.investigator --db db/ai-pilot.sqlite3 list
python -m core.investigator --db db/ai-pilot.sqlite3 export db/ai-review.json
```

`--ai` explicitly sends each finding's allowlisted fields to the configured model.
It is not automatic redaction. The scope and unrelated API response fields are not
sent. Use synthetic data for the first live test. One request per task attempt,
45-second SDK timeout, no SDK retries, and at most three explicit attempts per task.
The default run limit is 10; the allowed range is 1–100.

The model returns a hypothesis, proposed fix, verification steps and evidence ID.
Malformed responses or unsupported evidence IDs fail the task. Schema validation
is not factual verification: a human must review recommendations. No tools,
shell execution, SAP credentials, code edits or external messaging are exposed
to the model. A valid response always ends at `needs_review`, never `resolved`.

## Failure and restart handling

```bash
python -m core.investigator retry 1
python -m core.investigator run --ai
```

Failed tasks record exception class only, avoiding provider error strings that
might expose credentials. Check model/key configuration for `ValueError`, SDK
installation for `ModuleNotFoundError`, or provider availability for SDK errors.
Original evidence remains intact. Do not retry after correcting evidence; import
the corrected comparison to create a distinct task instead.

After a crash, running tasks remain visible. **Stop the old worker process first**,
then explicitly recover its task; this prevents two workers operating on it:

```bash
python -m core.investigator retry 1 --recover-interrupted
```

SQLite transactions prevent two healthy workers claiming the same queued task.
Use a local filesystem, not a shared network filesystem. The database and exports
contain input evidence; store them under ignored `db/` and protect them accordingly.

## Validation and present limits

```bash
python -m unittest discover -s tests -p test_investigator.py -v
```

Twelve standard-library tests cover persistence, deduplication, scope isolation,
atomic input validation, concurrent claims, evidence preservation, response
validation, retry limits, error redaction, recovery, audit export and a mocked SDK.
The live provider has not been tested. The complete Flask regression suite should
run in repository CI with its pinned dependencies.

This is a reviewable pilot, not the full DeepSeek super-agent. There is currently
no web dashboard, GitHub event listener, autonomous code-repair worker, scheduler,
auto-PR creation, or SAP write-back. Run the CLI when a comparison is ready. The
next useful increment is an explicit `agent-ready` GitHub intake and isolated
code-repair executor, once the investigation output has been evaluated on real,
sanitisable examples. Keep human merge approval and separate client environments.
